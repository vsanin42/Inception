# User documentation

This document explains how to use and operate the infrastructure provided by this project from the perspective of an end user or administrator. It describes the provided services, how to start and stop the project, how to access the website and administration panel, where credentials are located, and how to verify that all services are running correctly.

## Overview of the provided services

This project deploys a small web infrastructure composed of three services, each running in its own Docker container.

**Nginx** acts as the public entry point to the infrastructure. It handles **HTTPS** connections and forwards PHP requests to WordPress using **FastCGI**. It is the only service exposed to the host machine.
**WordPress**, running with **PHP-FPM**, provides the website itself, including both the public-facing pages and the administration panel. PHP-FPM executes PHP code and communicates internally with the database. **MariaDB** is responsible for persistent data storage. It stores all WordPress-related data such as users, posts, media metadata and configuration options.

All services communicate internally through a **Docker-managed network**. Direct access to WordPress or MariaDB from the host is not required and is intentionally not exposed.

## Starting and stopping the project

The infrastructure is managed using **Docker Compose**. A **Makefile** is provided to simplify common operations.

All commands must be executed from the root directory of the repository.

### Starting the infrastructure

To build the images and start all services in detached mode, run the default Makefile target or the `up` rule. This creates the required directories for persistent data (if they do not already exist), builds the Docker images, and starts all containers in the correct order.

### Stopping the infrastructure

To stop and remove the running containers without deleting stored data, use the `down` rule in the Makefile.

### Cleaning the environment

To stop containers and remove images while keeping persistent data, use the `clean` rule.

To completely reset the project and delete all stored data, use the `fclean` rule. This removes local volume directories and results in a clean state on the next startup.

## Accessing the website and administration panel

### Website access

The website is accessed through **Nginx over HTTPS**.

Before opening it in a browser, ensure that:

* the correct **domain name** is present in the `/etc/hosts` file

* a self-signed **TLS certificate and private key** have been generated and placed in the expected directory

According to the project requirements, the domain name must follow the format `login.42.fr`, where `login` is the student username.

When accessing the site for the first time, the browser may display a security warning. This occurs because the certificate is self-signed and not issued by a trusted Certificate Authority. In this controlled environment, it is safe to accept the warning and proceed.

### WordPress administration panel

The WordPress administration interface is available by appending `/wp-admin` to the website address.

Log in using the administrator credentials defined in the `.env` file.

## Credentials and configuration management

### Environment variables

Configuration values and credentials are provided through an `.env` file, which must not be committed to version control. These variables include:

* database name and credentials

* WordPress administrator credentials

* WordPress user credentials

* domain name

The required variables can be identified in the MariaDB and WordPress entrypoint scripts. If a required variable is missing, the corresponding container will fail to initialize.

Any change to the `.env` file requires restarting the containers for the changes to take effect.

### TLS certificates

Nginx requires a **TLS certificate and a private key** to serve HTTPS traffic. These files must be generated by the user and placed in the directory expected by the Nginx configuration.

The certificate and key must never be shared or committed to the repository.

## Checking that services are running correctly

### Container status

The status of all containers can be inspected using Docker Compose commands. This allows verification that containers are running and whether they are marked as **healthy**.

### Logs

Logs from all services are redirected to standard output. They can be viewed using the Makefile `logs` rule or directly through Docker Compose logging commands.

### Healthchecks

Each container defines a **healthcheck**, which is executed periodically inside the container to verify that the service is operational.

Some services depend on others being healthy before starting. For example:

* WordPress waits for MariaDB to be healthy

* Nginx depends on WordPress being available

If a container is marked as unhealthy, its logs should be inspected first.
